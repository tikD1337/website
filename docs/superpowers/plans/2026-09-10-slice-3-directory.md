# Срез 3: каталог и учётные записи

> **Для агентов-исполнителей:** ОБЯЗАТЕЛЬНЫЙ ПОД-SKILL —
> `superpowers:executing-plans`.

**Цель:** появляется вторая половина работы первой линии — учётные записи.
Блокировки, сбросы паролей, членство в группах, и главное — **проверка
личности как обязательный шаг перед любым изменением аккаунта**.

**Спека:** `../specs/2026-09-09-helpdesk-simulator-design.md`
**Предыдущий срез:** `2026-09-10-slice-2-remote-desktop.md`

## Глобальные ограничения

Те же, что в срезах 1–2, плюс:

- Каждая операция над учётной записью проходит через `authorize`.
- **Консоль и команда — оба представления, операция одна.** Правило из
  среза 2 действует и здесь: `net user /active:no` и кнопка в консоли
  вызывают одну функцию из `core/directory/accounts.ts`.
- Дизайн интерфейса в этом срезе не переосмысливаем — используем уже
  сложившиеся правила (цвет означает суждение, скругление означает
  интерактивность) и существующие классы.
- `git add` только явными путями.

## Решение, которое определяет срез

Соблазн — заблокировать кнопку «Сбросить пароль», пока личность не
подтверждена. Это ошибка, и она обесценивает тренажёр.

**Правило: граница обозначается, а не прячется.** Сброс пароля без
подтверждения личности остаётся **технически выполнимым**: шлюз его
пропускает, изменение происходит, но оно помечается как
несанкционированное и оценка снимает балл по коммуникации и полномочиям.

Обоснование прямо из разбора оригинала: «сброс пароля для
неподтверждённого обратившегося — инцидент безопасности, а не услуга».
Инцидент нужно **совершить и увидеть последствия**, иначе техник не
поймёт, почему порядок важен. Спрятанная кнопка учит, что границ нет —
их просто не показывают.

Отличие от защитных служб: там действие невозможно физически (доменная
политика), здесь возможно и является ошибкой суждения. Разные правила
для разных природ запрета.

### Задача 3.1: Модель каталога

**Файлы:** `src/core/world/types.ts`, `seed.ts`, тест `directory.test.ts`

`WorldState.org` дорастает до дерева:

```
ous[]      path, name, parent
groups[]   name, displayName, ou, description,
           members[], grantsAccessTo[], protected
users[]    + ou, enabled, lockedOut, lockoutSource,
           pwdExpired, pwdLastSet, badPwdCount, groups[]
shares[]   path, requiresGroup, description
```

Дерево по образцу оригинала: домен → Corp → Employees (по отделам) ·
Workstations · ServiceAccounts · Servers · Groups (Security /
Distribution) · Admin (Tier0 / Helpdesk).

- [ ] Тест: каждый пользователь лежит в существующей OU
- [ ] Тест: членство двусторонне согласовано (user.groups ↔ group.members)
- [ ] Тест: группы Tier0 помечены `protected`
- [ ] Тест: каждая общая папка требует существующую группу
- [ ] Тест: `cloneWorld` копирует каталог глубоко

### Задача 3.2: Операции над учётными записями

**Файлы:** `src/core/directory/accounts.ts`, тест

```
unlockAccount(world, sam, session, clock)          → OpResult
resetPassword(world, sam, session, clock)          → OpResult
setEnabled(world, sam, enabled, session, clock)    → OpResult
addToGroup(world, sam, group, session, clock)      → OpResult
removeFromGroup(world, sam, group, session, clock) → OpResult
```

Каждая: проверяет существование, идёт через `authorize`, пишет
`recordChange` с пометкой санкционированности.

- [ ] Тест: разблокировка снимает `lockedOut` и обнуляет счётчик
- [ ] Тест: сброс пароля без подтверждения личности **проходит**, но
      изменение помечено `authorized: false`
- [ ] Тест: сброс пароля с подтверждением помечен `authorized: true`
- [ ] Тест: добавление в защищённую группу Tier0 отклоняется
- [ ] Тест: добавление в группу согласованно меняет обе стороны
- [ ] Тест: несуществующая учётка даёт внятную ошибку

### Задача 3.3: Проверка личности

**Файлы:** `src/core/directory/identity.ts`, тест

Проверка не кнопка «я подтвердил», а сверка ответа с карточкой каталога
по контрольному полю (например, отдел или руководитель).

```
verifyIdentity(world, sam, field, answer, session, clock) → boolean
```

- [ ] Тест: верный ответ поднимает флаг `identityVerified`
- [ ] Тест: неверный ответ флаг не поднимает
- [ ] Тест: попытка сверки пишется в журнал общения
- [ ] Тест: подтверждение относится к конкретной учётке, а не «вообще»

### Задача 3.4: Команды net и dsquery

**Файлы:** `src/core/terminal/commands/net.ts`, `dsquery.ts`, тест

- [ ] Тест: `net user` неизвестного даёт ошибку 2221
- [ ] Тест: `dsquery user` фильтрует по OU

### Задача 3.6: Сценарий с блокировкой

**Файлы:** `src/scenarios/identity-account-lockout.ts`

Учётная запись заблокирована. Причина — кэшированные старые учётные
данные на телефоне, который раз в пять минут пробует войти. В журнале
контроллера домена видно источник блокировок.

Ловушка: сброс пароля вместо разблокировки формально сработает, но
телефон заблокирует учётку снова. Правильный путь — разблокировать
**и** сказать пользователю убрать старый пароль с телефона.

- [ ] Цель требует выяснить источник блокировки
- [ ] Тихая поломка: не сказал про телефон → заблокируется снова
- [ ] Сквозной: образцовое прохождение даёт `full`
- [ ] Сквозной: сброс пароля без подтверждения личности валит вердикт
- [ ] Сквозной: разблокировал, не разобравшись в источнике → `partial`

### Задача 3.7: Сценарий с доступом к папке

**Файлы:** `src/scenarios/identity-share-access.ts`

Нет доступа к общей папке: пользователь не в нужной группе.

Ловушка: выдать доступ напрямую, минуя группу. Формально работает,
но при следующем аудите прав это аномалия, и новый сотрудник отдела
получит ту же проблему. Правильный путь — добавить в группу.

Плюс: изменение членства применяется только после повторного входа —
это часть тренировки, а не придирка.

- [ ] Тихая поломка: доступ выдан вне группы
- [ ] Сквозной: добавление в группу даёт `full`
- [ ] Сквозной: обход группы даёт `fail`
