# Срез 6В — база знаний

> Спека подсреза. Общая спека: `2026-09-09-helpdesk-simulator-design.md`,
> разделы 3.1 и 7 («Документация»). Дорожная карта: задачи 6.7–6.8.
> Предыдущие подсрезы — 6А (серверная) и 6Б (активы и логистика).

## Зачем

База знаний не пишется автором тренажёра — она зарабатывается игроком.
Каждый закрытый тикет с заметкой становится черновиком статьи; техник
правит, публикует, архивирует. Через смену тот же сценарий приходит
снова, и в тикете видна собственная статья: вы читаете то, что писали
сами, и видите, насколько это помогает.

Критерий успеха: база пуста на старте; закрытие тикета с заметкой
создаёт черновик; статья правится с новой версией, публикуется и
уходит в архив; всё переживает перезагрузку; в тикете видны статьи по
той же проблеме.

## Решения, принятые без пользователя

Пользователь 27.09: «делай что посчитаешь нужным, не нужно каждый раз
спрашивать», на 6В — «да давай».

| Вопрос | Решение | Почему |
|---|---|---|
| Сколько статей на проблему | Одна на сценарий; повторное закрытие того же сценария добавляет тикет в источники, текст не трогает | Иначе каждая смена плодила бы дубли, а «известная проблема» — одна |
| Какие закрытия дают черновик | Любые с непустой заметкой, кроме «Отменено пользователем» | Плохая заметка даёт плохой черновик — и это урок, а не повод фильтровать |
| Где хранится | В прогрессе рядом с историей (IndexedDB) | Статьи заработаны игроком и обязаны пережить перезагрузку, как история |
| Старое хранилище без статей | Читается как «статей нет» | Поле добавочное; сбрасывать всю историю из-за его отсутствия — потерять прогресс на ровном месте |
| Создать статью с нуля | Нельзя | «Наполняется закрытыми тикетами» — механика оригинала; ручные статьи превратили бы базу в блокнот |
| Влияние на оценку | Никакого | Оценка считает работу по тикету; чтение своей статьи — законный приём, а не доказательство |
| Название инструмента | «Документация», как в навигации оригинала | Паритет |

## Модель

```ts
type KbType = 'sop' | 'runbook' | 'network' | 'ad' | 'known-issue' | 'vendor' | 'diagnostics'
type KbStatus = 'draft' | 'published' | 'retired'

interface KbVersion { version: number; at: string; title: string; type: KbType; body: string }

interface KbArticle {
  id: string              // 'KB-0001' — по порядку создания
  scenarioId: string      // ключ «одна статья на проблему»
  title: string           // по умолчанию — краткое описание тикета
  type: KbType
  body: string            // по умолчанию — заметка о решении
  status: KbStatus
  version: number         // 1 при создании, +1 на каждую сохранённую правку
  category: string; subcategory: string
  resolutionCode: ResolutionCode   // код первого закрытия
  createdAt: string; updatedAt: string
  sources: string[]       // id прохождений (`смена:номер`), из которых статья выросла:
                          // номер тикета выводится из сценария и у повторов одинаков
  history: KbVersion[]    // прежние версии, без текущей
}
```

Подписи типов: SOP, Runbook, Сеть, Справка по AD, Известные проблемы,
Вендоры, Диагностика. Статусы: черновик, опубликована, в архиве.

Тип черновика: код «Эскалация» → «Известные проблемы»; иначе по
категории: «Сеть» → «Сеть», «Личность» → «Справка по AD»,
«Оборудование» → «Диагностика»; прочее → SOP.

`Progress` получает `kb: KbArticle[]`. Проверка прочитанного принимает
прогресс без `kb` (прошлый формат) и достраивает пустой список; битая
статья — ошибка, как битая запись истории.

## Операции — `core/kb/`

- `draftFrom(kb, record): KbArticle[]` — новая база: черновик из записи
  прохождения или источник, добавленный к статье того же сценария.
  Чистая функция, базу не мутирует.
- `editArticle(a, patch, at): KbArticle` — новая версия: прежняя уходит в
  `history`, `version + 1`; правка без изменений версию не поднимает.
  Пустой заголовок или текст — ошибка.
- `setStatus(a, status, at)` — черновик → опубликована → в архиве →
  опубликована. Опубликовать пустое нельзя; вернуть в черновик нельзя.
- `searchKb(kb, { query, type, status })` — поиск по заголовку и тексту
  без учёта регистра, фильтры.
- `relatedTo(kb, ticket)` — статьи того же сценария, затем той же
  подкатегории; архивные не показываются.
- `mergeKb(loaded, inMemory)` — гидратация: загруженное первым; статья
  из памяти того же сценария сливает источники, остальные получают
  следующие номера.

## Стор

- `resolveTicket` после записи прохождения обновляет `progress.kb`
  через `draftFrom` синхронно, хранилище получает следом (правило
  среза 5).
- `editArticle(id, patch)`, `setArticleStatus(id, status)` — правят
  `progress.kb` и сохраняют.
- `openArticle(id)` — при взятом тикете пишет `kb:<id>` в осмотренное:
  разбор показывает, что техник заглядывал в базу, но баллов за это нет.
- Гидратация сливает `kb` через `mergeKb`.
- «Стереть прогресс» стирает и базу.

## Интерфейс

- **«Документация»** — новый инструмент: поиск, фильтры по типу и
  статусу, список (номер, заголовок, тип, статус, версия, источников);
  статья — текст, метаданные, история версий; правка — заголовок, тип,
  текст, «Сохранить» (новая версия), «Опубликовать», «В архив» /
  «Вернуть из архива». Пустая база объясняет себя: «Статьи появятся из
  закрытых тикетов».
- **Тикет:** раздел «База знаний» — похожие статьи; открыть — переход в
  «Документацию» на эту статью.
- **Разбор:** строка «Черновик статьи KB-0003 создан» или «Тикет добавлен
  к статье KB-0003» со ссылкой.

## Тесты

- `kb`: черновик — тип по таблице литералов, отменённое и пустое не
  создают; повтор сценария добавляет источник; правка — версия и
  история, пустое — ошибка; статусы — таблица переходов; поиск и
  похожие; слияние при гидратации.
- `validate`: прогресс без `kb` читается; битая статья — ошибка.
- стор: закрытие создаёт черновик синхронно и отдаёт в хранилище;
  правка и публикация сохраняются; `openArticle` пишет осмотренное
  только при взятом тикете.
- `e2e`: закрыть APIPA — черновик; новая смена, снова APIPA — в тикете
  видна своя статья, после закрытия у неё два источника.

## Чего в срезе нет

- Ручного создания и удаления статей.
- Баллов за использование базы.
- Совместной правки, комментариев, согласования публикации — это
  механики команды, а пользователь один.
