## Зачем

Первая линия видит инфраструктуру и обязана понимать, где кончаются её
полномочия. До этого среза сеть была плоским фактом: адаптер «лежал» в
сегменте `vlan20`, DHCP был флажком `dhcpHealthy`. Почему у машины нет
адреса, выяснить было нечем, кроме `ipconfig`, — а настоящий ответ часто
живёт на коммутаторе: порт не в том VLAN, ретрансляция DHCP пропала.

Критерий успеха: два новых сценария проходятся целиком через серверную и
консоль коммутатора, оценка засчитывает найденное и сделанное, а попытка
выйти за полномочия — отказ, который виден в разборе.

## Модель мира

### Коммутатор — источник истины для линка и VLAN

Решение: **линк и VLAN машины выводятся из порта, а не хранятся в
адаптере**. Хранить их и там и там значило бы синхронизировать две копии
— ровно то, от чего проект отказался в «подходе A».

- `Adapter.segment` удаляется. VLAN машины — `accessVlan` порта, в
  который она воткнута (`port.connectedTo === hostname`).
- `Adapter.linkUp` остаётся, но меняет смысл: **физика со стороны
  машины** — кабель вставлен, сетевая карта включена. Итоговый линк —
  `adapter.linkUp && port.adminUp`; без порта линка нет.
- Всё, что читало `a.linkUp` и `a.segment` (`ipconfig`, `ping`, трей),
  переходит на `core/network/link.ts`: `linkOf(world, host)`,
  `vlanOf(world, host)`, `segmentOf(world, host)`.

```ts
interface SwitchPort {
  name: string              // 'Gi1/0/22' — короткое имя, как в show
  description: string       // 'DESK-3-22'
  connectedTo: string       // hostname или '' — патч-корд, техник его не меняет
  mode: 'access' | 'trunk'
  accessVlan: number
  adminUp: boolean          // shutdown / no shutdown
  saved: { accessVlan: number; adminUp: boolean; description: string }
}

interface VlanInterface {   // SVI, только у ядра
  vlan: number
  ip: string; mask: string
  helpers: string[]         // ip helper-address — ретрансляция DHCP
  adminUp: boolean
}

interface NetSwitch {
  hostname: string; role: 'access' | 'core'
  vendor: string; model: string; serial: string; firmware: string
  location: string; mgmtIp: string
  vlans: Array<{ id: number; name: string }>
  ports: SwitchPort[]
  vlanInterfaces: VlanInterface[]
  log: Array<{ at: string; text: string }>    // show logging
  health: { cpu: number; memory: number; temperature: number; psu: 'ok' | 'fail'; since: string }
}
```

`saved` — стартовая конфигурация порта. `write memory` копирует текущее в
`saved`. Несохранённое изменение — тихая поломка: после перезагрузки
коммутатора порт вернётся в прежний VLAN. Путь адресуем выбором по полю:
`network.switches[hostname=SW-FL3-01].ports[name=Gi1/0/22].saved.accessVlan`.

### Сегменты и DHCP

`NetworkSegment` получает `vlanId: number` и `name`; строковый `vlan`
остаётся ключом. Добавляются сегменты `vlan10` «Servers» и `vlan40`
«Printers» (без DHCP: у принтеров статика).

DHCP-сервер переезжает в серверный VLAN (`DHCP01`, `10.20.10.5`): иначе
ретрансляция не нужна и сценарий про неё — неправда. Сервер отвечает
клиенту VLAN *n*, когда:

1. `segment.dhcpHealthy` — область на сервере обслуживается;
2. у ядра есть SVI для VLAN *n*, он поднят, и среди `helpers` есть
   `segment.dhcpServer`.

Функция одна — `core/network/dhcp.ts: dhcpServes(world, vlan)` — и её
зовут `ipconfig /renew`, подъём линка и серверная (счётчик запросов).

**Дефект, найденный по ходу:** `ipconfig /renew` выдавал любой машине
`leasePool[0]`, то есть `10.20.14.88` — адрес Priya Raman. Новая машина
получила бы чужой адрес. Сегмент получает `leases: Record<mac, ip>`
(засеян текущими адресами); аренда — прежняя по MAC или первая свободная.

### Серверная

`network.switches` (SW-FL3-01 доступа, CR-01 ядро), `network.routers`
(RT-EDGE-01), `network.servers` (DC01, DC02, DHCP01, FS01, MAIL01,
APP01), `network.printers` (PRN-FL3-01, в VLAN 40). У сервера: роль,
адрес, ОС, здоровье, службы (тип `Service` переиспользуется). Показатели

ретрансляции нет. Своего состояния серверная не хранит.

## Область тикета — `authorize`

Сессия знает свой инцидент: `createSession({ number, device, requester })`
вызывается в `claimTicket`. Новый вид действия:

| Действие | Решение |
|---|---|
| `infra-change` над портом, куда воткнута машина тикета | `allow` |
| `infra-change` над любым другим портом или без тикета | `deny`: «вне области тикета — нужна эскалация» |
| `shared-system` — SVI, `ip helper-address`, транк, служба сервера | `deny`, как и раньше |

`deny` записывается опасным действием, как любой отказ шлюза. Граница
обозначается, а не прячется: кнопки и команды есть, отвечают отказом.

## Консоль коммутатора

Чистая функция над миром, как команды Windows:
`runSwitch(line, cli, ctx) → { stdout, cli }`, где `cli` — режим
(`user` / `enable` / `config` / `config-if`) и текущий интерфейс. Режим —
состояние консоли, а не мира: живёт в сторе рядом с терминалом и
сбрасывается с инцидентом.

- Слова команд принимаются **по однозначному префиксу**, как в IOS:
  `sh int st`, `conf t`, `int gi1/0/22`, `sw acc vl 20`. Неоднозначный —
  `% Ambiguous command`, неверный — `% Invalid input detected at '^' marker.`
- В журнал сессии пишется и набранная строка, и **каноническая форма**
  (`CommandEntry.canonical`): цели сценария сверяются с канонической,
  заметка — с любой. Иначе сокращение наказывалось бы.
- Команды: `enable`, `disable`, `show interfaces status`, `show interfaces
  <if>`, `show vlan brief`, `show mac address-table [address <mac> |
  interface <if>]`, `show running-config interface <if>`, `show ip
  interface brief`, `show logging`, `configure terminal`, `interface <if>`,
  `switchport access vlan <n>`, `shutdown`, `no shutdown`, `description
  <текст>`, `ip helper-address <ip>`, `no ip helper-address <ip>`, `exit`,
  `end`, `write memory`, `copy running-config startup-config`.
- Отказ шлюза печатается как в IOS с AAA: `Command authorization failed.`
- Консоль и кнопки серверной вызывают **одни и те же** операции
  `core/infra/switchops.ts`: `setAccessVlan`, `setPortAdmin`,
  `setDescription`, `saveConfig`, `setHelper`. Тест на неотличимость
  обязателен.

Формат вывода — по документации IOS; живого железа под рукой нет, и это
записано как открытый вопрос: сверить при первой возможности, как
`ipconfig` сверяли с живой Windows.

### Подъём линка

Windows при подключении кабеля сама идёт за адресом. Поэтому переход
линка «вниз → вверх» (`no shutdown`) запускает на машине получение
аренды: `dhcpServes` — аренда, нет — самоназначенный адрес. Смена VLAN
при поднятом линке машину **не** трогает: техник обязан сам сделать
`renew` или передёрнуть порт — это и есть навык.

## Эскалация — своя оценка

До этого среза ни один сценарий не ждал эскалации, и оценка знала
только «починил и подтвердил». Для сценариев с `expectedResolution:
'escalate'`:

- **Коммуникация и качество решения** вместо `userConfirmed` требуют
  `userInformed`: заявителю сказали, что заявка передана и кому.
  Флаг ставит реплика техника с намерением `handoff` («передаю»,
  «эскалирую», «второй линии», «сетевой группе») или кнопка «Сообщить о
  передаче» в тикете.
- **Заметка**: часть «Внесённое изменение» становится «Что передано»:
  названа реально выполненная диагностика на сетевом устройстве и сам
  факт передачи. Часть «Чем подтверждено» — «Заявитель предупреждён».
- **Универсальная тихая поломка** «адаптер держит самоназначенный адрес»
  проверяется только при коде «решено»: эскалированная проблема и не
  обязана быть устранена.
- **Вторая линия чинит после передачи**: `Scenario.onEscalate` —
  патч, который применяется при закрытии кодом «эскалация», **после**
  оценки. Иначе сломанная ретрансляция жила бы до конца смены и делала
  непроходимыми следующие сетевые тикеты.

## Сценарии

### `net-wrong-vlan-port` — «Переехал за другой стол, нет сети»

Tomas Lindqvist пересел на стол 3-22. Розетка стола — порт Gi1/0/22,
где раньше стоял принтер, и порт остался в VLAN 40. DHCP в VLAN 40 нет —
машина на самоназначенном адресе.

- **Развилка:** выглядит как APIPA, но `release` + `renew` не помогают —
  DHCP в этом VLAN нет. Ответ на коммутаторе.
- **Путь:** `ipconfig /all` (MAC и 169.254) → найти порт по MAC (`show
  mac address-table address …`, `show interfaces status` или карточка
  порта) → увидеть VLAN 40 → `switchport access vlan 20` → `renew` или
  передёрнуть порт → `write memory` → подтверждение.
- **Ловушки:** статический адрес на машине (тихая поломка «DHCP
  отключён»); VLAN сменён, но не сохранён (тихая поломка: вернётся после
  перезагрузки); правка чужого порта (отказ).
- Исход: `solved`.

### `net-dhcp-relay-missing` — «С утра нет сети у нескольких человек»

После ночных работ на ядре пропал `ip helper-address` у `Vlan20`. У всех,
кто перезагружался с утра, самоназначенный адрес. Заявитель — Dumisani
Mbeki, AL-LPT-0601; у соседей то же самое.

- **Развилка:** первая линия находит причину, но починить её не может и
  не должна: это конфигурация ядра.
- **Путь:** `ipconfig /all` → масштаб («у соседей так же?») → DHCP01
  здоров, но запросов нет → `show running-config interface vlan 20` на
  CR-01 — ретрансляции нет, в журнале коммутатора правка в 02:14 →
  сообщить заявителю о передаче → эскалация с доказательствами.
- **Ловушки:** `ip helper-address` самому (отказ), перезапуск службы
  DHCP (отказ), статический адрес на машине (тихая поломка).
- Исход: `escalate`, `onEscalate` возвращает ретрансляцию.

## Интерфейс

- Новый инструмент в левой колонке — **«Серверная»**. Слева список
  устройств по типам, справа карточка с вкладками «Общее», «Здоровье»,
  «Диагностика»; у коммутатора ещё «Порты» и «Консоль».
- «Порты» — сетка 48 портов (состояние знаком и словом, не цветом:
  цвет в проекте означает только суждение), карточка порта с действиями
  «VLAN доступа», «Выключить/Включить», «Сохранить конфигурацию».
  Открытая карточка — доказательство наравне с командой:
  `gui:port:sw-fl3-01/gi1/0/22`, `gui:svi:cr-01/vlan20`,
  `gui:device:dhcp01`.
- Серверная читается всегда, меняется только по взятому тикету — как
  каталог.
- В тикете — кнопка «Сообщить о передаче».
- Скилл `frontend-design` — при вёрстке экрана, в пределах правил
  интерфейса проекта (системные шрифты, цвет только для суждения,
  скругление только у интерактивного).
