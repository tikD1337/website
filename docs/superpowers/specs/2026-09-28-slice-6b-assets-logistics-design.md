## Зачем

Часть поломок первая линия не чинит руками: сломанную док-станцию или
гарнитуру меняют. Для этого нужно знать, что за оборудование числится
за человеком и на гарантии ли оно (CMDB), и уметь оформить отправку —
замену на стол, возврат вендору, утилизацию. Отправка идёт не
мгновенно: тикет ждёт поставку, и в это время техник берёт следующий.

Критерий успеха: два новых сценария проходятся целиком через CMDB и
логистику; оценка видит, проверил ли техник гарантию, что отправил и
куда, дождался ли доставки и подтверждения; неверное решение по
гарантии видно в разборе; тикет, ждущий поставку, отпускает слот и
возвращается с сохранённым журналом.

## Решения, принятые без пользователя

Пользователь 27.09: «делай что посчитаешь нужным, не нужно каждый раз
спрашивать». Развилки решены так:

| Вопрос | Решение | Почему |
|---|---|---|
| Как тикет «ждёт» при правиле «один в работе» | Статус «Ждём поставку» отпускает слот; журнал, окна, консоли инцидента паркуются и возвращаются при повторном взятии | Иначе техник сидит без дела, пока едет курьер, — этого нет ни в жизни, ни в оригинале |
| Время | Настоящие часы стора и `tick()` раз в секунду; моменты этапов считаются от оформления, а не от момента тика | Детерминированно при любой частоте тиков; тесты двигают инжектируемые часы |
| Длительность | Доставка на стол ~1,5 мин, вендор ~2,5 мин, утилизация ~1,5 мин | Ждать можно, скучать — нет; точных цифр оригинала разведка не сняла |
| Исправность периферии | Хранится в CMDB (`condition`), диспетчер устройств выводит строки периферии из CMDB | Один источник истины: замена в CMDB чинит машину без синхронизации двух копий |
| Кто меняет CMDB | Только операции логистики; вручную — нет | Карточка актива — факт учёта; ручная правка учила бы «поправить запись вместо дела» |
| Утилизация оборудования на гарантии | `flag` шлюза: проходит, помечается, стоит вердикта | Ошибка суждения, а не невозможное действие — как сброс пароля без сверки |
| RMA без гарантии | Проходит; вендор отклоняет, актив возвращается на склад неисправным | Последствие в мире, а не запрет: тихая поломка «неисправное числится запасом» |
| Входящие поставки | Есть в модели и в журнале логистики; оформляет закупка, не первая линия | Паритет с восемью типами оригинала без чужих полномочий |

## Модель мира

### CMDB — `world.cmdb: Asset[]`

```ts
type AssetKind = 'laptop' | 'desktop' | 'dock' | 'monitor' | 'headset'
  | 'phone' | 'cable-kit' | 'switch' | 'router' | 'server' | 'printer'
type Lifecycle = 'in-use' | 'in-stock' | 'in-transit' | 'rma' | 'retired'

interface Asset {
  tag: string              // 'AL-P2031' — P периферия, L ноутбук, D десктоп, N сеть
  kind: AssetKind
  vendor: string; model: string; serial: string
  owner: string            // samAccountName или ''
  lifecycle: Lifecycle
  location: string         // 'Стол 3-20', 'Склад, стеллаж B2', 'Серверная, стойка A2'
  purchased: string        // ISO-дата
  warrantyUntil: string    // ISO-дата; гарантия действует, пока now < warrantyUntil
  hostname: string         // для компьютеров и сети — имя в мире; иначе ''
  attachedTo: string       // для периферии — к какой машине подключена; иначе ''
  condition: 'ok' | 'faulty'
  note: string             // последняя отметка логистики: «Отклонено вендором: гарантия истекла»
}
```

Фильтры инструмента, как в оригинале: компьютеры (`laptop`, `desktop`),
периферия (`dock`, `monitor`, `headset`, `phone`, `cable-kit`), сеть и
серверы, склад (`lifecycle === 'in-stock'` любого вида).

Засев (`world/seed-cmdb.ts`): все машины мира; у каждого ноутбука док и
монитор на столе владельца, у десктопа — монитор; гарнитуры у двоих;
телефоны у троих; сетевое железо, серверы и принтер серверной; склад —
два дока, монитор, три гарнитуры, кабельный комплект, два подменных
ноутбука; один списанный ноутбук. Бренд периферии — `Halyard`, телефонов
— `Bramble`.

### Периферия в диспетчере устройств

`core/device/peripherals.ts: peripheralsOf(world, host)` — строки для
диспетчера устройств из активов с `attachedTo === host`: док
`Halyard D6000 USB-C Dock`, гарнитура `Halyard H340 USB Headset`,
монитор `Generic PnP Monitor`. Неисправный док — `problemCode: 43`,
`Windows has stopped this device because it has reported problems. (Code 43)`.
Неисправная гарнитура электрически исправна: диспетчер её видит
здоровой — это и есть находка «дело не в драйвере».

### Отправления — `world.shipments: Shipment[]`

```ts
type ShipmentType = 'headset-to-desk' | 'phone-rma' | 'cable-kit'
  | 'dock-monitor-swap' | 'vendor-rma' | 'inbound' | 'loaner' | 'disposal'

interface Shipment {
  id: string               // 'SHP-1041' — по порядку
  type: ShipmentType
  direction: 'to-desk' | 'to-vendor' | 'to-disposal' | 'to-warehouse'
  assetTag: string
  ticket: string           // номер тикета; у входящих — ''
  destination: string      // 'Стол 3-20 (Elena Varga)', 'Halyard — сервисный центр'
  createdAt: string
  stage: number            // индекс в этапах типа
  history: Array<{ stage: string; at: string }>
  tracking: string         // 'HX 4402 1187 RU' — выводится из id
  outcome: '' | 'accepted' | 'rejected'   // только у вендорских
}
```

Таблица типов (`core/logistics/types.ts`): русское имя, направление,
допустимые виды активов, этапы с длительностью. Этапы:

| Направление | Этапы | Длительности, с |
|---|---|---|
| на стол | оформлено → собирается на складе → у курьера → доставлено | 15 · 30 · 45 |
| вендору | оформлено → передано курьеру → у вендора → решение вендора | 20 · 60 · 60 |
| утилизация | оформлено → вывезено → утилизировано | 30 · 60 |
| на склад (входящее) | в пути → принято складом | 120 |

`advanceShipments(world, now): ShipmentEvent[]` — единственное место,
где двигается статус. Каждый этап наступает в момент
`createdAt + сумма длительностей`, а не в момент вызова: тик раз в
секунду и тик раз в минуту дают один и тот же мир. Эффект этапа
применяется ровно один раз, при переходе.

Эффекты:

- **Оформление на стол** (`createShipment`): актив со склада —
  `lifecycle: 'in-transit'`, место «В пути: <назначение>».
- **Доставлено на стол:** актив — `in-use`, владелец — заявитель тикета,
  место — его стол, `attachedTo` — машина тикета (для периферии). Прежний
  актив того же вида, подключённый к той же машине, отключается
  (`attachedTo: ''`) и остаётся на столе с прежним состоянием учёта —
  его надо вернуть или утилизировать отдельным отправлением.
- **Оформление вендору / в утилизацию:** актив сразу `in-transit`,
  `attachedTo: ''` (курьер забирает).
- **Решение вендора:** гарантия действует — `outcome: 'accepted'`, актив
  `rma`, место «Сервисный центр <вендор>»; не действует — `rejected`,
  актив возвращается `in-stock`, место «Склад, возврат от вендора»,
  `note: 'Отклонено вендором: гарантия истекла'`, состояние остаётся
  `faulty`.
- **Утилизировано:** актив `retired`, владелец `''`.
- **Входящее принято:** актив `in-stock` на складе.

## Отправка — через шлюз

Новый вид действия `shipment` в `authorize`:

| Действие | Решение |
|---|---|
| нет взятого тикета | `deny`: «нет открытого тикета — отправка оборудования только по тикету» |
| на стол — не заявителю тикета | `deny`: «вне области тикета — оборудование отправляется заявителю» |
| вендору / в утилизацию — актив не заявителя и не подключён к машине тикета | `deny`: «вне области тикета» |
| входящее | `deny`: «входящие поставки оформляет закупка» |
| утилизация актива на гарантии | `flag`: «утилизация оборудования на гарантии — вендор заменит его бесплатно» |
| остальное | `allow` |

Ошибки учёта, а не полномочий (без опасного действия): актив не найден;
вид актива не подходит к типу; на стол — актив не на складе; вендору или
в утилизацию — актив уже в пути, у вендора или списан.

`core/logistics/ship.ts: createShipment(world, input, session, clock)`
— единственная операция, и её зовёт кнопка инструмента «Логистика».
Изменение пишется в журнал сессии: путь `shipments[id=SHP-1041]`,
было `null`, стало `'<тип> <тег> → <назначение>'`. Заметка, назвавшая
номер отправления или тег актива, засчитывает часть «Внесённое
изменение» (имя из селектора пути — правило среза 6А).

## Тикет ждёт поставку

- `TicketStatus` += `'pending-shipment'` — «Ждём поставку». Ставится
  только при незавершённом отправлении на стол по этому тикету; правило
  в сторе (`waitForShipment`), кнопка лишь его отражает.
- Статус **отпускает слот**: `q.assigned = null`. Журнал инцидента,
  вывод терминала, консоли и окна паркуются в сторе по номеру тикета.
- Доставка по тикету в «Ждём поставку» переводит его в «В работе» и
  дописывает рабочую заметку «<время> Отправление SHP-1041 доставлено».
  Тикет ждёт в очереди со строкой «доставлено — можно продолжать».
- Повторное взятие тикета с парковкой **восстанавливает** журнал, окна и
  консоли. Правило «журнал принадлежит инциденту» становится точнее:
  другой тикет — другой журнал, свой тикет — свой журнал, даже после
  перерыва.
- `claim` больше не сбрасывает статус взятого тикета, кроме «Новый» →
  «Назначен».

Тикет можно не парковать: остаться в нём и дождаться доставки.
Закрыть до доставки тоже можно — но заявитель честно скажет, что
замены ещё нет, и подтверждения не будет.

## Оценка

Своей арифметики срез не добавляет: цели с доказательствами-состояниями
мира, тихие поломки сценария, флаг шлюза за утилизацию на гарантии.

- `inspectObject('asset', tag)` — открытая карточка актива засчитывается
  как `gui:asset:<тег>`.
- Открытое окно удалёнки засчитывается как `gui:app:<id>`
  (`gui:app:devmgmt`): «посмотрел диспетчер устройств» становится
  доказательством, как уже было с журналом событий.
- Путь условий принимает составной выбор: `cmdb[attachedTo=AL-LPT-0512&kind=dock].condition`
  — «исправен ли док, подключённый к машине заявителя», без знания
  тега, который техник выберет со склада.

## Сценарии

### `hw-dock-failed` — «Не работают мониторы и мышь через док»

Elena Varga, AL-LPT-0512, стол 3-20. Док `AL-P2031` (Halyard D6000,
куплен 2025-03-10, гарантия до 2027-03-10) неисправен: Code 43 в
диспетчере устройств. Ноутбук сам по себе работает.

- **Путь:** диспетчер устройств → Code 43 у дока → просьба переподключить
  кабель дока (не помогает) → карточка дока в CMDB: гарантия действует →
  «Замена дока/монитора» со склада на стол → «Ждём поставку» → после
  доставки звонок, подтверждение → «RMA вендору» для старого дока →
  заметка, код «решено».
- **Ловушки:** утилизация дока на гарантии (флаг шлюза); старый док не
  отправлен никуда — числится в работе за заявителем (тихая поломка);
  закрытие до доставки (нет подтверждения).

### `hw-headset-worn` — «Трещит гарнитура, пропадает микрофон»

Sam Okafor, AL-DSK-0192, стол 2-08. Гарнитура `AL-P3017` (Halyard
H340, куплена 2023-02-01, гарантия до 2025-02-01 — истекла) изношена:
треск при движении провода. Диспетчер устройств видит её исправной.

- **Путь:** диспетчер устройств — устройство исправно, дело не в
  драйвере → просьба подключить в другой порт (не помогает) → карточка
  гарнитуры: гарантия истекла → «Гарнитура на стол» со склада → после
  доставки подтверждение → «Утилизация» старой → заметка, код «решено».
- **Ловушки:** RMA вендору — вендор отклонит, гарнитура вернётся на
  склад неисправным запасом (тихая поломка «следующий техник отправит её
  кому-нибудь на стол»); старая не утилизирована — числится в работе.

Общих ресурсов у сценариев нет: склад общий, но запаса хватает на оба,
а ресурс только сужал бы окно смены. Машины разные.

## Интерфейс

- **«Активы»** — новый инструмент: фильтры (все, компьютеры, периферия,
  сеть и серверы, склад), поиск по тегу, модели, владельцу; таблица
  (тег, вид, модель, владелец, учёт, место, гарантия до); карточка
  актива. Истёкшая гарантия — словом «истекла», не цветом: это факт, не
  суждение.
- **«Логистика»** — новый инструмент: форма «Оформить отправление» (тип,
  актив — список подходящих по типу, назначение выводится, тикет —
  взятый), журнал отправлений (номер, тип, актив, куда, тикет, этап
  словом и «шаг 2 из 4», до следующего этапа — «0:40»). Отказ шлюза и
  ошибка учёта — словами под формой.
- **Тикет:** в рабочем статусе — «Ждём поставку» (выключен без
  отправления на стол); список отправлений тикета.
- **Очередь:** тикет в «Ждём поставку» и «доставлено — можно продолжать».
- **Часы:** `tick()` раз в секунду из `App` — заодно оживают часы на
  панели задач удалёнки, застывшие со старта смены.

## Тесты

По правилам CLAUDE.md «Какие тесты писать»:

- `logistics`: этапы по часам — один тик после всех сроков равен тикам
  каждую секунду; эффекты доставки, вендора (гарантия есть и нет),
  утилизации; входящее принимается складом.
- `ship`: таблица отказов и ошибок учёта литералами; флаг за утилизацию
  на гарантии; запись в журнал изменений.
- `peripherals`: строки диспетчера из CMDB; неисправный док — Code 43.
- `path`: составной выбор.
- стор: парковка и восстановление журнала; доставка возобновляет тикет;
  `tick` без отправлений ничего не меняет.
- `e2e`: образцовый проход каждого сценария с двиганием часов; развилки
  — утилизация на гарантии, RMA без гарантии, закрытие до доставки.
